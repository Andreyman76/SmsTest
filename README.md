### Имеется некий сервер, принимающий запросы по протоколу HTTP с Basic аутентификацией
Для тестирования был написан свой HTTP/gRPC сервер. К сожалению, тела запросов HTTP и gRPC не совпадают, что не позволило настроить *gRPC JSON Transcoding* для HTTP, вместо этого написан дополнительный HTTP сервис.

### Примеры запроса и ответа приведены в Приложении №2
Я допускаю, что идентификаторы могут быть строковыми, но более всего меня смутили строковые значения для *Quantity*, причем в proto это double. Тем не менее, данный контракт реализован. 
Для *Price* тоже используется double, что странно. Для подобных значений более приемлемо использовать decimal.

```json
{ 
	"Command": "SendOrder", 
	"CommandParameters": 
	{ 
		"OrderId": "62137983-1117-4D10-87C1-EF40A4348250", 
		"MenuItems":
		[ 
			{
				"Id": "5979224", 
				"Quantity": "1" 
			}, 
			{ 
				"Id": "9084246", 
				"Quantity": "0.408" 
			} 
		]
	}
}
```

В HTTP содержимое заказа называется *MenuItems*, а в gRPC - *OrderItems*, что более корректно. *OrderId* генерируется случайный, в задании не сказано, откуда его брать.


### Записать результаты выполнения метода в таблицу в БД
Не совсем понятно, какой результат выполнения метода нужен: успешно/ошибка, полученный список блюд, иные данные. Решено хранить данные, которые используются в *SmsTest.ConsoleApp* после получения меню и описываются нижеприведенной сущностью.

```cs
internal sealed class Dish
{
    /// <summary>
    /// Идентификатор блюда
    /// </summary>
    public required string Id { get; set; }

    /// <summary>
    /// Название блюда
    /// </summary>
    public required string Name { get; set; }

    /// <summary>
    /// Артикул блюда
    /// </summary>
    public required string Article { get; set; }

    /// <summary>
    /// Цена блюда
    /// </summary>
    public required double Price { get; set; }
}
```

При получении меню таблица очищается, записываются новые данные. Подобное целесообразнее делать на SQLite, а не на PostgreSQL.

## Задание №2
### Приложение должно предоставлять возможность чтения и изменения некого набора переменных среды в графическом формате. Внешний вид UI должен соответствовать изображенному в Приложении №4. 
Судя по скриншоту, пользователь имеет возможность создавать строки в *DataGrid* (самый первый столбец со звездочкой), однако по условию сказано, что пользователь может только читать и изменять значения строго заданному множеству переменных. Решено не реализовывать функционал добавления. 
Для стилизованных кнопок закрыть/свернуть используются иконки *Material Design Icons*, в оригинале похоже на символы 'X' и '-'.

### Вводимые Пользователем значения переменных могут быть только текстовые и на практике не иметь ограничений по длине
В приложении никакие ограничения не установлены, однако максимальная длина одной переменной среды на уровне ядра ОС составляет 32767 символов в Windows.

### При запуске производится чтение переменных и вывод их на экран, либо инициализация значениями по-умолчанию, если какая-либо из переменных не существует
В качестве значения по умолчанию назначается строка 'default'.

### Все записанные переменные и их значения должны быть доступны другим приложениям и сохраняться даже после перезапуска ОС
Решено использовать переменные среды для текущего пользователя (User), т.к. в отличие от Machine не требует прав администратора, а в отличие от Process доступно другим приложениям и сохраняется между запусками ОС.

### Подключить конфигурационный файл appsettings.json, в котором описать набор имен используемых переменных среды в виде массива строк
Также, на скриншоте есть столбец *Комментарий*, в таком случае для хранения переменных не получится ограничиться лишь массивом строк. Ниже приведена текущая схема, совместимая с DI в *SmsTest.Wpf*.

### Все факты изменения переменных среды должны фиксироваться в файл логов, формат названия следующий: test-sms-wpf-app-yyyyMMdd.log
В лог пишется лишь факт изменения переменной: выводится только имя переменной, старое/новое значение не выводится.
